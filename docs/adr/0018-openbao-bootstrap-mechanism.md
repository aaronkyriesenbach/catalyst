# OpenBao's own bootstrap mechanism: self-init, per-cluster granularity, no operator

Status: accepted

ADR 0004 deliberately left OpenBao's own one-time bootstrap open. This ADR settles it: use OpenBao's
built-in **self-initialization** feature (`openbao.org/docs/configuration/self-init/`) as the entire
storage-init/unseal/first-boot-config mechanism, paired with the already-chosen Static Key auto-unseal —
fully declarative, checked into `apps/openbao.ts`, zero human action.

## Decision

**Self-init covers the entire known first-boot config in one shot**: the KV-v2 mount for app secrets,
the Kubernetes auth method + role for platform-cluster ESO, the Kubernetes auth role for
[#42](https://github.com/aaronkyriesenbach/catalyst/issues/42)'s cluster-registration CronJob, and the
JWT auth method + one role per workload cluster (External/Internal) for SPIRE-authenticated ESO
instances ([#49](https://github.com/aaronkyriesenbach/catalyst/issues/49), ADR 0014). Self-init's own
`initialize` stanza runs arbitrary API requests exactly once, on first boot against empty storage, using
an ephemeral root token it generates and revokes itself — no `operator init`, no human ever handling root
key material. The one real contingency: SPIRE's OIDC Discovery Provider must already be live at that one
moment, since self-init has no retry — but this is a sequencing note for implementation, not new tooling,
and OpenBao disaster-recovery restores from a Raft backup (preserving everything self-init already
created) rather than re-running self-init from empty storage.

**Granularity is per-cluster, not per-app** — three fixed identities forever (platform-cluster ESO,
External-workload-cluster ESO, Internal-workload-cluster ESO), matching [#49](https://github.com/aaronkyriesenbach/catalyst/issues/49)'s
already-decided design and today's `external-secrets.ts` precedent (one shared `ClusterSecretStore`,
not per-app scoped). Per-app policies were considered and rejected: SPIRE (ADR 0014) only solves
_authentication_ (proving identity), never _authorization_ (OpenBao's own role/policy mapping) — so
per-app granularity is achievable in principle, but ESO has no native SPIFFE Workload API provider today
(open upstream issue, `external-secrets/external-secrets#6235`); making it work would need a bespoke
per-app JWT-SVID delivery/rotation sidecar per app namespace (`SecretStore` is namespace-scoped and can't
share a controller-wide identity the way per-cluster does), plus an ever-growing set of OpenBao
roles/policies as apps migrate ([#31](https://github.com/aaronkyriesenbach/catalyst/issues/31)'s
incremental cutover). Real per-app infrastructure for isolation gains not currently needed.

**No config-management operator.** `vault-config-operator` (redhat-cop) and `bank-vaults/vault-operator`
were both surveyed — neither has reliable OpenBao support: `bank-vaults` requires manually repointing at
an OpenBao image (not in its CI matrix) and has a known-broken active-service-selector incompatibility on
OpenBao ≥2.2.0; `vault-config-operator` has an open, unresolved discussion acknowledging recent OpenBao
changes aren't accounted for.

**Ongoing administration is a seeded human account, not a script or operator.** Self-init also enables
the `userpass` auth method and creates a persistent `superuser` admin account (the exact pattern shown in
OpenBao's own self-init docs), with the password sourced the same way ADR 0011 sourced Omni's own
bootstrap admin password: generated by the bootstrap-layer OpenTofu, stored in AWS Secrets Manager,
pulled into an in-cluster Kubernetes Secret via ESO's existing `aws-secrets-manager` `ClusterSecretStore`,
and referenced as an env var self-init's `env` data source reads at boot. This account is the sole
ongoing administrative door — a human runs `bao login` + ordinary `bao auth enable`/`bao policy write`
by hand for the handful of rare later changes this will ever need (the certain example: enabling
OpenBao's OIDC method once [#13](https://github.com/aaronkyriesenbach/catalyst/issues/13), human
identity provider, lands). No standing Job, CronJob, or ArgoCD sync hook is warranted for something this
infrequent, for a single operator.

**Where this lives**: an ordinary `apps/openbao.ts` `Application` on the platform cluster — self-init
config embedded in the Helm chart's values (or a mounted config file), no separate bootstrap-layer
mechanism. Consistent with ADR 0004's framing that this is owned by whatever reconciles the platform
cluster's apps.

## Considered Options

- **Helm post-install Job / hand-rolled idempotent script running on every deploy** (the original framing
  in ADR 0004 and this ticket's own initial scoping) — rejected once self-init's actual one-shot,
  root-token-based design was understood: it's unnecessary machinery for a first-boot-only concern, and
  the wrong shape for the rare later changes that genuinely need a live authenticated write (a human with
  the seeded admin account is simpler and proportionate).
- **`vault-config-operator` / `bank-vaults` for ongoing reconciliation** — rejected: unofficial/breaking
  OpenBao support in both, confirmed against upstream issues/discussions.
- **Per-app KV/auth granularity** — rejected for now: real isolation benefit, but blocked on ESO's missing
  native SPIFFE support and requires an ever-growing per-app write mechanism this ticket's simpler
  per-cluster answer avoids. Revisit if ESO ships SPIFFE support and per-app blast-radius containment
  becomes a priority.
- **Guarantee #13's human identity provider is live before OpenBao's first boot**, to also self-init its
  OIDC auth method — rejected: unlike SPIRE (a settled ADR), #13 is deliberately undecided until much more
  of the platform lands; OpenBao sits near the base of this rearchitecture's dependency graph ([#42](https://github.com/aaronkyriesenbach/catalyst/issues/42),
  [#49](https://github.com/aaronkyriesenbach/catalyst/issues/49), every app's eventual secrets migration)
  while human OIDC login is admin convenience only — inverting that order would stall the whole platform
  for a feature nothing else depends on, and wouldn't even fully solve the problem (any future IdP swap
  would face the same one-shot wall again).

## Consequences

- `apps/openbao.ts` needs: the OpenBao Helm chart with a self-init `initialize` config (KV mount, k8s
  auth + 2 roles, jwt auth + 2 roles, userpass auth + 1 superuser account), Static Key auto-unseal
  config, and NAS-backed storage (per ADR 0004).
- A new bootstrap-layer OpenTofu resource: a generated admin password written to AWS Secrets Manager,
  alongside Omni's own admin password (ADR 0011) in the same category.
- `apps/external-secrets.ts` gains one more `ExternalSecret` (the OpenBao admin password, AWS SM →
  in-cluster Secret) feeding OpenBao's own Helm values — a bootstrapping dependency: this must exist
  before OpenBao's chart installs.
- Implementation-time sequencing constraint: SPIRE (with its OIDC Discovery Provider live) must be
  deployed before OpenBao's very first boot, or the JWT auth portion of self-init needs `allow_failure`
  and a documented manual follow-up.
- OpenBao's own OIDC auth method for human login (deferred to #13) will be enabled by hand, once, using
  the seeded `superuser` account — not tracked as a further wayfinder ticket.
